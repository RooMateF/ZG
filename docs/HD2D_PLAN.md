# HD-2D 改版計畫

把《末日第十四天》從純文字版做成 HD-2D 風格（像素角色立在 3D 場景，景深、光暈、打光），保持回合制。

**目標平台：PC。** 手機版已放棄（2026-11-18 決定，原因見下），但保留幾個便宜的移植入口。

這份文件是給之後接手的人（或新的 Claude 對話）看的。對話紀錄不會跟著專案走，決定和進度都記在這裡。

## 現況（2026-11-18）

| 項目 | 狀態 |
|---|---|
| 文字版 | 完成且可玩。28 項情境測試、兩個機器人、選單走訪都通過。規則細節在 `DESIGN.md`。 |
| 引擎 | 選定 Godot 4.7.2。PC 用 Forward+ 渲染，手機平台自動退回 Mobile 模式。 |
| 外觀測試專案 | `hd2d/`：一個房間、三個像素角色、景深與光暈，全部程式產生，沒有美術檔。 |
| 操作 | 方向鍵、WASD、手把左搖桿上下左右走；滑鼠點地板會走過去。沒有虛擬搖桿。 |
| PC 上的實際畫面 | **還沒人看過。** 開發機是沒有顯示卡的虛擬機，Forward+ 的 SSAO 和體積霧只寫了程式，沒有實際看過效果。要等搬到有顯卡的電腦。 |
| 手機測試（已結束） | 0.1、0.2 版在使用者的 Android 手機上功能正常。回饋：畫面簡陋，像二十年前的 Minecraft。這是預期中的，因為完全沒有美術檔。 |
| 美術來源 | **未決定**，是目前最大的問題。 |
| 規則核心 | 沿用 Python 版，還沒接到畫面。 |

## 平台決定：為什麼放棄手機

使用者不喜歡虛擬搖桿的玩法。而「上下左右自由走動」是確定的需求，這在手機上幾乎一定要虛擬搖桿，兩者衝突。所以改成 PC 專用。

**保留的移植入口**（都不花額外成本，或成本很低）：

1. **輸入走動作名稱**（`move_left` 等，在 `main.gd` 的 `_setup_input` 綁定），不直接讀按鍵。加新裝置只改一處。
2. **點地板移動**。滑鼠點地板走過去，這在觸控螢幕上天然成立，將來手機版可以用它取代虛擬搖桿。
3. **渲染雙軌**。`project.godot` 設了 PC 用 Forward+、手機平台用 Mobile。Forward+ 才有的效果（SSAO、體積霧）在程式裡有條件判斷，Mobile 模式會跳過，畫面仍然成立。
4. **Android 匯出設定保留**。`hd2d/export_presets.cfg` 和 `hd2d/build_apk.bat` 還在，已驗證能在沒有顯示卡的機器上無畫面建出 APK。不再每個階段測，但隨時可以建一個出來看。
5. **規則和畫面之間維持窄介面**（見架構決定）。將來要上手機，只需要把介面後面的規則換成引擎內的實作，畫面不用動。

**不保留的**：手機效能調校、觸控介面尺寸、每階段雙平台測試。

## 參考風格

- 探索：Octopath Traveler 1／2 的城鎮，立體模型感的場景加移軸景深，角色可以上下左右自由走。
- 戰鬥：敵人在左、我方在右的橫向站位，上方行動順序列，敵人弱點圖示。

## 可行性結論

**程式面做得到。** 文字版的規則（戰鬥、時間、噪音、感染、隊友、據點、三個結局）和畫面是分開的，可以整套沿用。

**兩個瓶頸：**

1. **美術**。HD-2D 的質感主要來自像素角色、場景貼圖和特效。程式可以做打光、景深、著色器，但畫不出那個水準的像素圖。沒有美術來源就只能做到「技術上是 HD-2D、看起來是方塊人」。選項：買素材包、外包、AI 生成後人工修、自己畫。最快的驗證是找一套免費授權的像素素材包換上去，看差多少。
2. **定位改變**。文字版的目標是上班能偷玩，HD-2D 版是另一個產品。文字版保留，繼續當規則的唯一來源。

## 架構決定

- **引擎：Godot 4.7.2**。免費、專案檔是文字（好做版控和自動產生）。
- **渲染：PC 用 Forward+**，可以用 SSAO、體積霧、較好的陰影。
- **規則核心：沿用 Python，當裁判。** 畫面端把玩家的動作送給 Python 規則程式，拿回新的狀態和訊息來顯示。PC 上可以把 Python 一起打包。
  - 理由：規則還在頻繁修改，只維持一份才不會兩邊不同步。現有的 28 項測試和機器人繼續有效，平衡不用重調。放棄手機之後，這條路重新可行，省掉之前估的三成工程量。
  - **介面要窄**：畫面端只透過「送出指令、取得狀態」這兩件事和規則溝通，不直接讀規則內部。這是將來移植的入口，也讓畫面端可以用假資料獨立開發。
  - 這個決定是可以反悔的。如果將來要上手機，把介面後面換成引擎內的實作，再用 Python 版當對照組逐步對帳。
- **介面照 PC 設計**：鍵盤、滑鼠、手把。
- **存檔**：每一步自動存檔的設計沿用。

### 文字版機制怎麼對應

| 文字版 | HD-2D 版 |
|---|---|
| 地區（15 個） | 每區一個場景，房間是可走進去的室內景，上下左右自由走 |
| 城市地圖 | 地區之間的路線圖 |
| 距離 1～4 | 敵我之間的站位格 |
| 隊友上前／退後 | 前排／後排 |
| 瞄準、推開、牽制、集火、逃跑 | 戰鬥指令選單，旁邊標成功率和扣分原因 |
| 沒發現你（潛行搜索） | 探索畫面上敵人背對或遠離，有成功率提示 |
| 噪音條、時間、飢渴 | 常駐介面 |

## 團隊分工

假設團隊由多個 AI 代理分工，使用者是決策者。

| 角色 | 負責 | 備註 |
|---|---|---|
| 製作／PM | 範圍、里程碑、待辦、驗收、整合 | 主對話擔任 |
| 遊戲設計 | 把文字版機制轉成戰鬥站位、探索、介面規格 | |
| 規則工程師 | Python 規則、與畫面溝通的介面 | 沿用現有程式 |
| 畫面工程師 | Godot 場景、戰鬥演出、選單、輸入、打包 | |
| 技術美術 | 打光、景深、著色器、像素圖匯入流程 | HD-2D 的「樣子」由它負責 |
| 試玩 | 照正常玩法跑完整局，回報卡關、看不懂、無聊 | 手感和畫面只有人能判斷 |
| 品保 | 回歸測試、介面測試、存檔相容、效能 | |
| 對抗 | 專門找漏洞：刷物品、卡死、跳過流程、無腦必勝 | 與試玩分開，目的相反 |
| 審查 | 每次改動合併前由沒寫那段的人看過 | 是關卡不是常設職位 |
| 美術與音效 | 角色、敵人、場景貼圖、特效、音樂 | 代理填不了，要人決定來源 |

初期四個就夠：製作兼設計、一個工程師、技術美術、一個兼品保和對抗的驗證者，加上審查關卡。內容量產時再拆開。

## 階段

| 階段 | 做什麼 | 過關條件 |
|---|---|---|
| 0 準備 | 版控、引擎、美術來源、規則與畫面的介面 | 都有答案 |
| 1 外觀驗證 | 一個房間、一個會走的像素角色、打光加景深，換上真的像素素材 | 在有顯卡的電腦上看了覺得方向對；不對就在這裡停損 |
| 2 戰鬥切片 | 一場真的戰鬥，規則走 Python：行動順序、站位、瞄準、推開、逃跑、隊友、牽制 | 結果和文字版同種子一致 |
| 3 垂直切片 | 一整個地區可玩：探索、搜索、背包、一個 NPC、日夜光線、存讀檔 | 能玩 30 分鐘不出錯 |
| 4 內容量產 | 15 個地區、8 個生存者、勢力、三個結局 | 進度取決於美術供應 |
| 5 打磨 | 音效、平衡、打包發佈 | |
